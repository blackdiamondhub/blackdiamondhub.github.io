Self-hosted · Open source · Runs on wall screens

The home screen for a ski lodge.

Black Diamond Hub runs the touch screens on the walls of Black Diamond Lodge in Sun Peaks, BC. Guests get lift status, the shuttle, restaurants and the hot tub temperature. The house gets heat, lights, speakers and cameras. Every feature is an app, installed from a catalog and run in its own locked-down container.

What it does

One screen for the mountain, the lodge and the people staying in it. Every tile is live, and every screen below is a separate app.

On the mountain

Lift and trail status, the snow report, resort webcams, the village shuttle with live arrivals, restaurants that are open now and resort events.

In the lodge

Radiant floor heat by zone, lights, shades, fans, fireplaces and the garage, house-wide Sonos, exterior lights and a shared family calendar, all driven through Home Assistant.

For guests

Stays that preheat the house before guests arrive, Wi-Fi QR codes, kitchen timers, a restaurant shortlist to send to your phone and a feedback box.

Everything is an app

The hub itself is a small shell: home screen, settings, accounts and a broker. Features ship as apps, each in its own repository with its own releases.

1

Publish

An app repo tags a release. Shared CI builds a Python wheel and attests where it came from.

2

Build

The catalog builds a container image from the wheel on a pinned runtime base, signs its provenance and opens a PR with the new entry.

3

Install

Settings → Apps → Store lists what the app asks for (Home Assistant entities, network, memory) before you install it.

4

Run

The supervisor verifies the signature, starts the container and the hub proxies it on its own port, waking it on demand.

Beta and stable channels

A pre-release version (2.3.0b1) is a beta. One house follows betas and tries them first; promoting a beta flips its catalog entry to stable with the same image, no rebuild.

One codebase, several houses

Everything that differs between houses (branding, home screen sections, which apps are baked in, per-app defaults) lives in a site folder. CI publishes one image per site.

Apps talk through the hub, not to each other

Containers get a broker token instead of credentials. Through it an app can read and call the Home Assistant entities it was granted, keep settings, secrets and state, subscribe to events, and publish or read shared data such as a calendar feed.

Small by design

Apps idle at well under 100 MB, and on-demand apps stop after ten idle minutes. The hub keeps showing their last status and wakes them when a screen opens them.

Security model

A house hub sees door locks, cameras and guests' stays. Apps are treated as untrusted code that has to ask for everything.

Signed supply chain

Wheels are pinned by SHA-256. Images are pulled by digest only, and only if a Sigstore/SLSA attestation from the catalog's build workflow vouches for that exact digest. A tampered catalog can't point at an image the builder didn't sign.

Least-privilege permissions

Apps declare grants like ha.read:climate.main_floor or ha.call:climate.set_temperature. The broker enforces them on every call and trims Home Assistant's registry to what the app may see. An update that asks for more needs approval again.

Network modes

Each app runs with none (no network at all), outbound (internet only) or lan, which the admin has to grant explicitly. Most apps need nothing but the hub.

Locked-down containers

Non-root user, read-only root filesystem, every Linux capability dropped, no-new-privileges, and limits on memory, CPU and process count.

Encrypted secrets

Passwords and API keys are stored with AES-256-GCM, bound to their app and name, with the key kept outside the database. Settings pages never show a secret again, and backups hold only ciphertext.

Rate limits and audit

Broker calls are rate limited per app and audited by app, operation and name, never by value. Containers never see the hub's environment.

Build an app

An app is a Django app plus a manifest. The bdh-sdk gives it tiles, settings, Home Assistant, speakers, events and shared data, and a reusable CI workflow that tests, releases and attests it.

# radiant/plugin.py (simplified)
from bdh_sdk import PluginSpec, Setting, Tile
from bdh_sdk.plugins import INT, NETWORK_NONE, LIFECYCLE_ON_DEMAND

spec = PluginSpec(
    id="radiant", app="radiant",
    urls="radiant.urls",
    status="radiant.homepage.status",  # live tile text
    tiles=(Tile(title="Radiant Heat", url_name="radiant",
                icon="radiant/hub/icon.svg", section="lodge"),),
    settings=(Setting("setpoint_debounce_s", "Setpoint debounce",
                      type=INT, default=10, unit="s"),),
    api_version=2,
    permissions=(
        "ha.read:climate.main_floor",
        "ha.read:sensor.thermux_*",
        "ha.call:climate.set_temperature",
    ),
    network=NETWORK_NONE,          # no network beyond the hub
    lifecycle=LIFECYCLE_ON_DEMAND,  # sleeps when idle
    memory_mb=96,
)
# radiant/views.py
from bdh_sdk import ha

def set_zone(request, entity_id, target):
    ok, err = ha.call_service(
        "climate", "set_temperature", entity_id,
        {"temperature": target})
    ...

# .github/workflows/ci.yml
jobs:
  hub:
    uses: blackdiamondlodge/bdh-sdk/.github/workflows/app-ci.yml@v0
    with:
      app_id: radiant

Tag a release and the rest is automatic: the catalog builds and signs the image, the hubs on the beta channel offer the update, and the store shows anything new the app asks for. Apps can also add screen saver pictures, info-strip stats, homepage cards, shortcuts and share data with other apps.

Architecture

Everything runs on hardware in the house. The internet is only needed to install or update apps, and for apps that fetch outside data.
